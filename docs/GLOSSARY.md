# Glossary

Every name Chamberlain's schema, configuration, logs and docs use, what it means here, and the industry term it follows.
The rule behind this page: **a name for a table, a column, a state, a mode or a feature is the established industry term when
one exists for the same concept and is used the same way.** Where Chamberlain's concept really differs, it keeps a name of
its own and says why. A new name goes in this file in the same change that adds it.

Three words are easy to mix up, so they come first:

- An **item** is what monitoring tools call an *alert* or an *incident*: a thing that needs attention, tracked in the `items` table.
- A **notification** is a message sent *about* an item. Chamberlain's notification, sent to the Steward, is called a **wake**.
- A **wake** is a notification that starts an agent turn in the Steward's thread. It is Chamberlain's own word (see [Wakes and delivery](#wakes-and-delivery)).

Sources are linked where a term follows one. Where the third column says *Chamberlain-specific*, no established term fits and
the reason is given.

| Rights record (state `rights-sent`) | What the Steward was last sent of its rights and rulings: a hash of the thread, rights and rulings (the away mandate is not in it), its context size then, and `at`, when the full text went out. A changed hash, a shrunk context or no record sends the full block. | Cache validator (ETag) | Chamberlain keeps the usual meaning: the hash says "unchanged", so only the pointer line is sent. |
| Rights stamp (`rights_for` on `outbox` and `held_wakes`) / rights-first wake | A wake carrying the rights pointer records the Steward thread, session and rights hash it was composed for. A Steward wake queued before stamps existed (before migration 9), or imported, is stamped `legacy-unstamped` whatever its text, and always gets the rights first. | Message ordering with a preceding context message (send the prerequisite first, then the unchanged message) | Chamberlain never edits a queued message: outbox rows are immutable and their text is never searched. |
| Hand-off wake (`steward-handoff:<session>`) | The wake the daemon queues when the health check says HAND OFF, telling the Steward to run its hand-off now. An outbox row like any other: retried, then dead-lettered. | Self-healing / automatic failover | The daemon starts the hand-off; the Steward does it. Needs the adapter's `handoffInstruction`; without it the operator is asked. |
| Hand-off / brief (`steward-brief.md`) | The text a new Steward reads first: its rules, rulings, mode and open work. | Handover note | Chamberlain-specific: it is generated from the database plus written notes, for an agent rather than a person. |
| Brief fragment (`brief.d/*.md`) | A markdown file in the config directory's `brief.d/`, appended verbatim to the generic hand-off in byte order of filename. Only regular `.md` files are read; symlinks and anything else are ignored with a warning. Fragments are authority config: `brief.d/` and each fragment must be owned by the effective uid and not group- or world-writable (0600 and 0644 are fine), else they are skipped with a warning (`authorityProblem`, `src/core/private.ts`). A `brief.d/` or fragment that cannot be read (say a 0300 directory) is skipped with a warning naming it and the error; the hand-off still comes out. | Drop-in file (a `.d` directory of fragments merged in lexical order) | [systemd.unit(5), drop-in directories](https://www.freedesktop.org/software/systemd/man/latest/systemd.unit.html) |
| Table `state` | Small named JSON records: the sweep clock, `rights-sent`, the health verdict, the heartbeat, the hold gate's clock. | Key-value store | Kept for now. The name is overloaded (an item also has a `state`, and there is a state *directory*), but the table is internal and nothing outside `src/core/` names it. |
| Table `events` and the *log* | The append-only log of what the daemon did: `fire`, `skip-*`, `alarm`, `answered`, `state-moved`... Read with SQL by `queue-waits.ts` and the return brief. | Event log / audit log | Kept. The rows are Chamberlain's own record, not [CloudEvents](https://github.com/cloudevents/spec/blob/main/cloudevents/spec.md) (which `id`, `source` and `subject` echo only loosely). |

## Items: the one thing that is tracked

| Term | Definition | Standard term | Source or reason |
| --- | --- | --- | --- |
| Item (table `items`) | One row for anything tracked, de-duplicated or re-notified: a sweep finding, a decision-queue question, an alarm, a record of a wake that went out, something held for the operator's return. | Alert (Alertmanager, PagerDuty) / incident / work item | Kept as `item`, the generic word: a queue question is not an alert. |
| `source` | Who produces the item: `check:<name>`, `runaway`, `queue`, `notification-log`, `card-answer`, `alarm`, `held`. | Integration (PagerDuty), monitor (Datadog) | Kept. Both of those are narrower (they only monitor); `source` also covers the queue and the alarms. PagerDuty's own `source` field means the affected system, which is not this. |
| `kind` | What the item is: `finding`, `evaluation_error`, `question`, `sent`, `alarm`, `hold`. | Type | Kept. |
| `dedup_key` (TS `dedupKey`; a finding's `dedupKey`) | Stable identity, unique per source. Observing the same key again is the same item; a resolved one that returns is a new occurrence. | `dedup_key`: "a string which identifies the alert triggered for the given event" | [PagerDuty: Send an alert event](https://docs.pagerduty.com/developer/send-alert-event). Alertmanager uses a *fingerprint* of the label set for the same job ([configuration](https://prometheus.io/docs/alerting/latest/configuration/)); Chamberlain's key is chosen by the source, not computed. Was `key`. |
| `state` | `triggered`, `acknowledged` or `resolved`. | Incident status: triggered, acknowledged, resolved | [PagerDuty incidents](https://docs.pagerduty.com/incident-management/incidents/overview). *Triggered*: created, notifying. *Acknowledged*: being handled, notifications stop even if new triggers arrive. *Resolved*: fixed; a later trigger with the same key opens a new one. Was `open` / `woken` / `acknowledged` / `resolved`: `open` became `triggered`, and `woken` is gone, because whether anyone was notified is the notification count, not a state. |
| Triggered | Seen and unresolved. | PagerDuty *triggered* | As above. (Prometheus's *pending* and *firing* describe an alert rule's evaluation: "Elements that are active, but not firing yet, are in the pending state", [alerting rules](https://prometheus.io/docs/prometheus/latest/configuration/alerting_rules/). An item has no evaluation window, so they do not fit.) |
| Acknowledged | Learned of and quiet until it recurs: a seeded finding, a question set aside with "not now". | PagerDuty *acknowledged* | As above. |
| Resolved | Gone, answered or delivered; kept for the record until pruned. | PagerDuty *resolved* | As above. |
| Occurrence | One run of an item from first seen to resolved. A recurrence reopens the row with its counters reset. | Alert/incident recurrence | PagerDuty: "later trigger events with the same key open a new alert" once one is resolved. |
| `first_seen`, `last_seen` | When this occurrence was first and last observed. | `firstSeen`, `lastSeen` | [Sentry issue details](https://docs.sentry.io/product/issues/issue-details/). (Alertmanager's webhook payload has `startsAt` and `endsAt` for the same purpose; [configuration](https://prometheus.io/docs/alerting/latest/configuration/).) |
| `mode`: `live` | Notifies for real. | - | The default; no special term. |
| `mode`: `silenced` | Tracked, never notifies. Questions and held entries use it: their arrival is not news, their answer is. Was `off`. | Silence | Alertmanager: "Silences are a straightforward way to simply mute alerts for a given time." A silence is time-bound and matcher-based; a source's `silenced` mode is permanent, but the effect (still tracked, never notified) is the same. [Alertmanager](https://prometheus.io/docs/alerting/latest/alertmanager/) |
| `mode`: `shadow` | Runs the real decision and records what it *would* have sent, in counters of its own, notifying nobody. Going live starts from a true zero. Was `log`. | Shadow mode / shadow deployment | A shadow deployment runs on real traffic and its output is withheld: [Arize](https://arize.com/glossary/shadow-deployment/), [Qwak](https://docs.qwak.com/docs/shadow-deployment). Not a *dry run* (below): it persists and runs for as long as you like. |
| Notification | A message sent about an item. The item's notification columns count the ones sent. | Notification | [Alertmanager](https://prometheus.io/docs/alerting/latest/alertmanager/): an alert is the condition, a notification is what is sent about it. Chamberlain's was "alert" used as a verb ("the item alerts"). |
| `notification_count`, `next_notification_at` | Live notifications sent, and when the next one is due. A count above zero *is* the "notified" flag. Were `alert_count`, `next_alert_at`. | Notification log entry | Alertmanager keeps the same fact in its [notification log](https://pkg.go.dev/github.com/prometheus/alertmanager/nflog). |
| `shadow_notification_count`, `shadow_next_notification_at` | The same pair, for shadow mode. Were `would_alert_count`, `would_next_alert_at`. | - | Kept apart so a month in shadow never counts as notifications sent. |
| Repeat policy (`RepeatPolicy`: `intervalsMs`, `maxNotifications`) | After the n-th notification the next comes `intervalsMs[n-1]` later (the last interval repeats), until `maxNotifications`. Helpers: `NOTIFY_ONCE`, `repeatEvery(ms, max)`, `repeatAtIntervals(ms[], max)`. A finding asks for it with `repeatIntervalMs` and `maxNotifications`. Was the "ladder" (`Ladder`, `stepsMs`, `cap`, `repeatMs`, `maxAlerts`). | Repeat interval | `repeat_interval`: "How long to wait before repeating the last notification." ([Alertmanager configuration](https://prometheus.io/docs/alerting/latest/configuration/)). *Escalation* is not the right word: PagerDuty's escalation policy notifies the *next* responder after a delay, while a repeat policy re-notifies the *same* recipient. |
| `decideNotification` (`src/core/notification.ts`) | The one function that says whether an item notifies now. Only `ItemStore.observe` calls it. Was `decideAlert`. | - | Chamberlain's invariant, enforced by `src/architecture.test.ts`. |
| `subject_kind`, `subject_id` | What the item is about: a pull request, a run, a deploy, a thread. | `subject` | CloudEvents: "the subject of the event in the context of the event producer" ([spec](https://github.com/cloudevents/spec/blob/main/cloudevents/spec.md)). |
| `payload` | JSON: a finding's text, a question's content, a hold's details. | Payload | - |
| Finding | One thing a source reports as needing attention: `{dedupKey, text, repeatIntervalMs?, maxNotifications?, baseline?, subject?}`. | Alert instance / event | Kept: it is a source's *report*, before it becomes an item. |
| `baseline` | A finding learned silently the first time its source runs: a standing condition that is not news. It starts `acknowledged`. | Baseline | A baseline records what already exists so only new findings are reported; [Bandit's `baseline` option](https://bandit.readthedocs.io/en/latest/ci-cd/github-actions.html) compares against one. |
| `evaluation_error` (kind and dedup key; `EVALUATION_ERROR`) | A source could not be evaluated: the check exited non-zero, printed nonsense or timed out. Its findings keep their state, one item notifies every run until it runs again, and the sweep becomes a full one. Was "blind" (`blind`, `BLIND`). | Error state | Grafana: "The Error state is triggered when the alert rule fails to evaluate its query" ([docs](https://grafana.com/docs/grafana/latest/alerting/fundamentals/alert-rule-evaluation/nodata-and-error-states/)). **Not** *No Data*: that is "the alert rule query runs successfully but returns no data points". For a Chamberlain check an empty list is a *clear* result, so No Data would mislead. Nagios's *UNKNOWN* is the same idea ([guidelines](https://nagios-plugins.org/doc/guidelines.html)). |
| Notification log (source `notification-log`, kind `sent`) | One item per wake that already went out, by dedup key, so none goes again. Was source `wake`, kind `fired`. | Notification log (`nflog`) | Alertmanager's `nflog` is an append-only log of notifications sent, used by its dedup stage ([nflog](https://pkg.go.dev/github.com/prometheus/alertmanager/nflog)). |

## The Alert Desk

The desk is a standing thread that reads every alert and says what it is (docs/alert-desk.md). Names follow Alertmanager and PagerDuty where they exist.

| Term | Definition | Standard term | Source or reason |
| --- | --- | --- | --- |
| Alert Desk (receiver `desk`) | The standing thread alerts are routed to, with its own wake URL and busy gate, sent by the one relay through its one serial queue. | Receiver | Alertmanager: a *receiver* is "a named configuration of notification integrations" ([configuration](https://prometheus.io/docs/alerting/latest/configuration/)). `receiver` is the outbox and held-wake column: absent is the Steward, `desk` is the desk. |
| Inbox (`inbox.jsonl`) | The file alert sources append one JSON line to, drained by the daemon: `{v, source, family, title, body, ts, severity}`. | Spool / queue | Kept: it is a plain append-only file that any process can write with one `write`, which is what a spool is. |
| Family (`family`) | The stable identity of one alert condition: two failing units are two families. Items of source `alert-desk` are keyed by it. | Group key / `dedup_key` | Alertmanager's *group key* and PagerDuty's `dedup_key` identify an alert the same way ([PagerDuty](https://docs.pagerduty.com/developer/send-alert-event)). The sources choose it; the drain does not compute it. |
| Window (item kind `window`, `windowMs`) | At most one wake per family per 15 minutes, however many events arrive. | `group_interval` | Alertmanager: "How long to wait before sending a notification about new alerts that are added to a group" ([configuration](https://prometheus.io/docs/alerting/latest/configuration/)). |
| Repeat (`repeatMs`) | An unchanged family wakes again after 24 hours; a changed one wakes at once. | `repeat_interval` | The same page. A change is a new occurrence of the item (`resolve`, then `observe`), as a returning alert is in PagerDuty. |
| Signature | What "changed" means for a family: its severity, its title and the first 300 characters of its body, with timestamps and numbers blanked. | Fingerprint | Alertmanager's *fingerprint* identifies a label set; this one identifies the content, so a counter ticking is not news. |
| Pending (item kind `pending`, mode `silenced`) | A wake the window or the cap held back, kept to go on a later pass. | Silence-and-hold | An item in mode `silenced` is tracked and never notifies (see `mode` above); nothing is dropped. |
| Daily cap (`dailyCap`) | At most this many alert wakes in a rolling 24 hours (0: no cap). Counted from the desk's own outbox rows. The desk is told once a day (item kind `cap-note`). | Rate limit | Chamberlain-specific: Alertmanager has none; PagerDuty rate-limits its Events API for the same reason. |
| Morning wake (item kind `morning`) | The first pass of each local day from `morningHour` sends one wake that runs the desk's Morning sweep. | - | Chamberlain-specific: it replaces the operator's 07:00 triage task. |

## Sources and the sweep

| Term | Definition | Standard term | Source or reason |
| --- | --- | --- | --- |
| Check (`sweep.json` `checks`, source `check:<name>`) | A command you configure. It prints findings as JSON and exits 0, or fails (an error). | Check | Nagios and Sensu: "Each check definition specifies a command and the schedule at which it should be executed" ([Sensu checks](https://docs.sensu.io/sensu-go/latest/observability-pipeline/observe-schedule/checks/); [Nagios plugin guidelines](https://nagios-plugins.org/doc/guidelines.html)). Chamberlain's checks print a list of findings instead of one status. |
| Item source (`ItemSource`) | Anything that can say what currently needs attention: a check, the runaway counter, a future monitor. | Data source / monitor | Kept `source`: see the item table. |
| Sweep (`sweep.ts`, `sweep.json`) | A timer (every two hours) that runs the sources, and every six hours a *full sweep*: the Steward is woken to supervise by judgement. | Rule evaluation (Prometheus's "evaluation interval") | Kept. A sweep is evaluation plus, every sixth hour, a scheduled supervision round with no standard name. `sweep.json` is the public config file. |
| Runaway (source `runaway`) | The built-in source: threads that started many turns of their own since the last sweep. | Runaway process | Kept as the plain-English name of the failure (a loop that keeps going). It is the one built-in detector, so it has no standard counterpart to borrow. |
| Heartbeat (state `heartbeat`) | The daemon's periodic record that it is alive, with its server list and failure counts. | Heartbeat | Standard. |
| Alarm (source `alarm`, `alertCommand`) | Chamberlain's own failure signal: the daemon cannot reach the Steward, a token is expiring, the queue is unreadable. An alarm is an item with a repeat policy and goes to your `alertCommand`, never to the Steward. | Dead man's switch / watchdog alert; meta-monitoring | PromLabs: "a watchdog alert (also sometimes called a 'dead man's switch', sentinel alert, beacon alert, or heartbeat alert)" ([end-to-end watchdog alerts](https://training.promlabs.com/training/monitoring-and-debugging-prometheus/metrics-based-meta-monitoring/end-to-end-watchdog-alerts/)). Kept `alarm` because it is a normal alert about the monitor itself, not a heartbeat that must keep arriving. |

## Wakes and delivery

| Term | Definition | Standard term | Source or reason |
| --- | --- | --- | --- |
| Wake | The message that resumes the Steward's thread: a notification, delivered by webhook, that starts an agent turn. | Notification / page | Chamberlain-specific. A pager notification asks a person to look; a wake *starts work* in an agent that was idle, and it batches (digest) and is gated on that agent being busy. "Wake" says what it does, and it is the word every prompt the Steward reads uses. |
| Delivery (`deliver.ts`, `relay.ts`, `deliveryId`) | Getting one wake to the transport: `deliver.ts` writes it as an outbox row, the relay sends it. `deliveryId` is the wake's message id, frozen in its row, sent with every POST of it (in the POST body and as the last line of the text). The Steward treats a delivery id it has already handled as a repeat. | Webhook delivery id | GitHub's `X-GitHub-Delivery` header: "A globally unique identifier (GUID) to identify the event" ([webhook events](https://docs.github.com/en/webhooks/webhook-events-and-payloads)). It is **not** an *idempotency key* in the strict sense: an [Idempotency-Key](https://datatracker.ietf.org/doc/draft-ietf-httpapi-idempotency-key-header/) is for the *receiver* to recognise a retry, and the T3 webhook does not. Chamberlain dedupes on its own side, and puts the item id in the text so the Steward can tell a repeat. |
| At-least-once delivery with bounded retries (`deliver.ts`, `relay.ts`) | The guarantee Chamberlain gives a wake: a row is POSTed until one POST is accepted **or** it has used `maxAttempts` attempts, and **no row is POSTed more than `maxAttempts` times between explicit retries**, every POST under the row's frozen delivery id and text; the receiver de-duplicates by that id. It is **not** "every wake is delivered": a row that used its attempts is a dead letter, and it can have **zero** accepted POSTs (even zero sent: an attempt is counted before its POST, so crashes between the count and the POST spend attempts with nothing sent). It says nothing about latency or order (see Head-of-line blocking and Best-effort ordering). The ways one row can be POSTed more than once are listed exactly in [ARCHITECTURE.md](ARCHITECTURE.md#delivery-guarantees-and-the-windows-that-remain): the transport accepted a POST and the daemon exited before committing it delivered; a POST that timed out after the webhook took it; an operator retry. | At-least-once delivery; bounded retries | [Transactional outbox](https://microservices.io/patterns/data/transactional-outbox.html): the relay "might publish a message more than once", so "a message consumer must be idempotent, perhaps by tracking the IDs of the messages that it has already processed". Bounded retries then a dead-letter queue: SQS's `maxReceiveCount` is "the number of times a consumer can receive a message from a source queue before it is moved to a dead-letter queue" ([SQS dead-letter queues](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-dead-letter-queues.html)). |
| Transactional outbox (tables `outbox`, `outbox_members`) | Every wake to send is a row, written in the **same transaction** as whatever made it necessary (a notification decision, a sweep's findings, the page's claim and answer). A row's delivery id, text and members are frozen when it is created (database triggers refuse a change); only its status (`pending`, `delivered`, `dead_letter`, `cancelled`), `attempts` and two times move. `outbox_members` binds each delivery id a row carries (its own, or a digest's members) to that one row, ever: its primary key is the UNIQUE constraint. The row's status is the delivered ledger; there is no other. Was `pending_wakes`, then a per-process outbox with a separate `delivered_wakes` ledger. | Transactional outbox | [microservices.io: Transactional outbox](https://microservices.io/patterns/data/transactional-outbox.html): "insert messages/events into an outbox table as part of the local transaction"; "a separate Message Relay process publishes the events inserted into database to a message broker". |
| Message relay (`src/core/relay.ts`) | The one component that sends wakes: it runs in the daemon only, polls the outbox (every second, `CHAMBERLAIN_RELAY_POLL_MS`, and at once when the daemon writes a row), composes held items into a digest row, commits `attempts + 1`, POSTs, and commits the row `delivered`. It cannot be built without the held one-relay lock (`createRelay` takes the handle `holdRelayLock` returned). The page, the sweep, `synthetic-wake.ts` and every other producer only insert rows, and no other process calls a wake transport. | Message relay; polling publisher | [microservices.io: Transactional outbox](https://microservices.io/patterns/data/transactional-outbox.html) names the sender the *Message Relay*; [Polling publisher](https://microservices.io/patterns/data/polling-publisher.html): "Publish messages by polling the outbox in the database." Not the `relays` table below, which is one forwarded answer. |
| Terminal state | A row that nothing will act on again: a `delivered` or `cancelled` outbox row that no unresolved claim names; an item `resolved`; an old event. Retention (`maintain.ts`) prunes only these, and a trigger refuses to delete a `pending` or `dead_letter` row. A pending row, a held wake, a dead letter and a claim whose wake is undelivered are **not** terminal, however old: they stay until delivered or explicitly cancelled. | Terminal state (of a workflow or state machine) | The state-machine term: a state with no outgoing transitions ([Wikipedia: finite-state machine](https://en.wikipedia.org/wiki/Finite-state_machine)). Used here for rows rather than states, with the same meaning. |
| `wake-not-ready` (alarm) | Raised when wakes are waiting and no wake URL is configured (or readable). They are kept, no attempt is used, and they go as soon as there is somewhere to send. | Unroutable message | A broker can silently drop a message it has nowhere to send; RabbitMQ lets a publisher ask for it to be returned or sent to an alternate exchange instead ([RabbitMQ publishers](https://www.rabbitmq.com/docs/publishers)). Chamberlain keeps the wake where it is and raises the alarm, for the same reason: a dropped alert is a lost one. |
| `wake-stale` (alarm) | Raised when a row or a held wake has waited undelivered for more than 24 hours. It is the only thing age does to a wake: the wake itself is kept. | Stale alert / dead-letter alarm | A dead-letter queue holds messages that could not be processed ([AWS SQS](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-dead-letter-queues.html)). Chamberlain keeps the wake where it is and alarms, because a daemon wake cannot be rebuilt from anything else. |
| Attempt cap (`maxAttempts`, `CHAMBERLAIN_MAX_ATTEMPTS`, column `outbox.attempts`) | The most POSTs one row gets before it is dead-lettered; default 3. The relay commits `attempts + 1` **before** each POST, so a crash, a timeout or a lost answer still counts it, and every outcome counts: an accepted POST, a refusal, a 5xx, a timeout. Nothing gives an attempt back. An attempt is not a POST: the count is committed first, so a crash before the POST spends an attempt with nothing sent, and a row can be dead-lettered with zero POSTs; the cap is per row between explicit retries (a retry resets it). A failed row waits one minute, then four, before its next attempt. With nowhere to send (`wake.ready()` false) nothing is attempted and nothing is counted. | Max delivery count / `maxReceiveCount` | Azure Service Bus: a message is moved to the dead-letter queue when "the delivery count ... exceeds `MaxDeliveryCount`" (default 10) ([dead-letter queues](https://learn.microsoft.com/en-us/azure/service-bus-messaging/service-bus-dead-letter-queues)); Amazon SQS: a redrive policy's `maxReceiveCount` ([dead-letter queues](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-dead-letter-queues.html)). Both count receives; Chamberlain counts sends, because a send is what can reach the receiver twice. |
| Dead-letter queue / dead-lettered wake (status `dead_letter` on `outbox`) | A row that used every attempt without being delivered. It is **kept where it is**, not sent again, and the `wake-dead-letter` alarm repeats until the operator decides. `bun src/wakes.ts list` shows it; `retry <id>` (only a dead letter) returns it to `pending` with its attempts at zero, the same id, text and members; `cancel <id>` makes it a tombstone. The relay never has a dead letter in flight, so a retry can never add a POST beside a live one. "Stuck" is the operator-facing word in older notes; "dead letter" is the state. | Dead-letter queue | A dead-letter queue holds messages that could not be processed after repeated attempts ([AWS SQS](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-dead-letter-queues.html); [Azure Service Bus](https://learn.microsoft.com/en-us/azure/service-bus-messaging/service-bus-dead-letter-queues)). Chamberlain keeps the row in the one outbox with a status instead of moving it to a second queue, so a recovered claim still finds the id. |

## Recovering a failed thread

| Term | Definition | Standard term | Source or reason |
| --- | --- | --- | --- |
| Recovery (`src/core/recover.ts`) | The daemon's own handling of a failed run: classify the error in code, retry once after a grace, and hand a second failure to the judge. No model decides whether to retry. Off unless `CHAMBERLAIN_RECOVER=1`. Its state (pings sent, failures per thread over a six-hour horizon, the judge's hold, pending retries, the breaker) is kept in the database's state table, so a restart sends no second first ping. | Failure kind (`FailureKind`) | What a run's error is, read from the backend's class, code and message by a table in code. ## Kept on purpose

`item`, `source`, `kind`, `check`, `sweep`, `runaway`, `wake`, `held` / `hold`, `digest`, `claim`, `relay`, `deliveryId`,
`acknowledged`, `resolved`, `baseline`, `alarm`, `heartbeat`, `subject`, `first_seen` / `last_seen`, `evidence`, `ruling`,
`decision`, `mandate`, `butler`, `steward`, `principal`, `away` and `dry run` keep their names, for the reasons in the tables.
The ones that agree with an industry term (`acknowledged`, `resolved`, `digest`, `check`, `baseline`, `subject`,
`first_seen`, `heartbeat`, `deliveryId`) say which. The ones that do not (`wake`, `held`, `claim`, `ruling`, `mandate`,
`butler`, `steward`, `sweep`) are Chamberlain's own vocabulary, and the tables say what they mean and why no standard term fits.
