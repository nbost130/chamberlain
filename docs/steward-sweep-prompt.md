<!-- TEMPLATE for the full supervision sweep the daemon sends every six hours, or when a routine check could not run.
     To customize it, copy it to ~/.config/chamberlain/sweep-prompt.md (mode 0600): the daemon reads that file first.
     {{principalName}} is replaced with the `principalName` setting. Keep one rule per numbered step. -->
Run this full supervision sweep quickly. Use small reads, and send a message only when a step needs action.

1. Runaway check. Read the tail of every running thread you supervise, on every machine. Count fix rounds per PR or unit. If any unit is starting a third fix round, or any thread loops on the same failure, steer it to stop. Hold the leftovers per your decision rights, and log with decided.
2. Stalls. Look for threads whose last turn ended on a promise with no armed wait, and for work that has sat with no activity for hours. Whoever started the thread, handle it: when the next action is clear and inside your decision rights, move it forward with exact steps; when a decision is pending, put it on {{principalName}}'s queue with `ask`; when it is finished, settle it. Leave it only when it is running, already has an open queue item or hold, or is a child whose parent is working.
3. Landing. Take reviewed, green PRs to merge, pinned to the reviewed head, after a disposition comment, if your decision rights give you that work.
4. Findings. Handle each finding the routine checks listed in this wake, if any.
5. New sessions, only while {{principalName}} is away. Only when there is idle, unblocked work you are not doing: save the work item’s full launch brief, title, workspace strategy and stable request ID together so another wake can resume it. Run `chamberlain models selection worker --project "<project>" --request-id "<id>"` on the Steward host (from source, `bun src/models.ts selection worker` with the same flags). When launching through T3, first call `t3_environment_links` and append one `--t3-environment <id>` to selection for the current environment and each reachable linked environment with launch access. If the link inventory fails, retain the work. A failed selection keeps the work pending. For a routed plan, use the returned adapter, destination and launch arguments. Start a fresh launch only when `reservation.acquired` is true. For T3, call `t3_thread_launch` with `environmentId` set to `launch.environmentId`, the exact `launch.modelSelection` including options, and `launch.projectId` with `reservation.attemptId` as clientRequestId, a worktree and a full brief. A legacy pin has no reservation or project ID; use the saved work request ID as clientRequestId and verify project and capacity on its selected host before launch. After a routed launch succeeds, run `chamberlain models confirm <id> <attemptId> <threadId>`. If the launch definitely created nothing, run `chamberlain models release <id> <attemptId>`. For a pending reservation after a crash or lost reply, replay the identical saved launch arguments on its recorded host with the same clientRequestId through the T3 launch tool, then confirm the returned thread. A confirmed reservation already supplies the threadId. With a harness that cannot reconcile by request ID, keep the work pending until the outcome is established. Never for anything that needs {{principalName}}'s gate.
6. Anything on the ASK list goes to {{principalName}}'s queue first, with `ask` (add `"urgent": false` when it can wait; it then sends no notification and is listed below the urgent ones), never to {{principalName}} mid-sweep as a message. Hold it only after that, with `afk hold ... --item <the Q-id ask printed>` (plus `--pr`, `--issue`, `--branch` or `--thread` if they apply). A hold with no `--item` is refused, and so is an ask or hold already settled (it prints the answer; act on that, or add `notSettled` / `--not-settled "<why>"` if it is truly a different question). A hold is a real wait on {{principalName}}, never an FYI; a new fact about an existing hold is `afk note <id> "<text>"`, not a second hold.

While {{principalName}} is marked away, the standing rules for it are the ones in the away record your wakes carry.

If nothing needed action, reply with one line: 'sweep HH:MM: nothing to do'.

A sweep wake carries a delivery id (the last line of the wake). The webhook cannot de-duplicate, so you do: if you have already handled a wake with that delivery id, it is a repeat. Reply 'repeat of DELIVERY-ID' in one line and do nothing else.
